# Spring Boot examples

The `examples/springboot` directory holds four small Spring Boot applications, and each one shows a different way to use
telescope in a Spring service. The table below lists them. If you want to see the widest range of features in one place,
start with `order-jpa`. The other three modules each focus on one topic.

| Module            | What it shows                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| `order-jpa`       | Runtime mappers and generated navigators side by side on an order domain stored with Hibernate |
| `product-starter` | `telescope-spring-boot-starter` collecting `Mapper` beans into a `TelescopeMapperRegistry`     |
| `org-chart`       | A runtime mapper over a Hibernate entity that refers to itself through a manager and reports   |
| `invoicing`       | Conversion classes generated by `@Bridge` for record and bean pairs, with no persistence layer |

## Stack

All four modules use the same versions, which come from each module's `build.gradle.kts`:

- Spring Boot 4.1.1, which manages Hibernate ORM 7 (7.4.5.Final at the time of writing), H2 and Jackson 3.
- A Java 25 toolchain, with sources compiled using `--release 21`, so the applications run on Java 21 or later.
- Lombok 1.18.48 in `order-jpa` and `product-starter`.

The `invoicing` module uses only the web starter, so it has no JPA, Hibernate or H2 dependency.

Each module has its own build file with no shared parent configuration, so you can copy one build file into another
project. Inside this repository the modules depend on sibling projects such as `project(":core")`,
`project(":codegen")`, `project(":lombok")` and `project(":spring-boot-starter")`, so a change in the library is checked
against the examples before a release. In your own project, replace each of those with the published artifact at version
2.0.0, as listed in the root README's [Install](../../README.md#install) section.

## `order-jpa`

The `order-jpa` module stores an `Order` record graph through Hibernate and shows most of the telescope API in one
application. The runtime API (`Telescope.of(Order.class).field(...)`) and the generated navigators
(`OrderTelescope.of().customer()`) are used side by side, and both work on the same domain types. The records carry
`@Focus` and the entities carry `@BeanFocus`, so the build generates a navigator and a `<X>FieldOptics` holder for each
of them. When a holder is present, the runtime mapper reads and rebuilds that type through it.

### Endpoints

| Method and path                                   | What it does                                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `POST /orders`                                    | Lowercases the customer email with `Telescope.of(Order.class).field(...).field(...).update(...)` |
| `GET /orders/{id}`                                | Loads the entity and converts it with `orderMapper.backward(...)`                                |
| `POST /orders/bulk`                               | Converts a list of orders with `orderMapper.liftList()`                                          |
| `PATCH /orders/{id}`                              | Overlays the non-null fields of a partial order with `orderMapper.patch(existing, partial)`      |
| `POST /orders/telescope`                          | Same as `POST /orders`, through the generated `OrderTelescope.of().customer().email()`           |
| `GET /orders/telescope/{id}`                      | Same as `GET /orders/{id}`                                                                       |
| `POST /orders/telescope/{id}/discount?percent=10` | Lowers every line item price by composing a navigator with `lineItemMapper.asTelescope()`        |
| `POST /orders/telescope/normalise-emails/{id}`    | Lowercases the stored customer email through the generated navigator                             |
| `POST /orders/validated`                          | Checks every line item quantity with `updateValidated` and returns all errors in one 400 body    |
| `POST /orders/{id}/bulk-update`                   | Applies only the fields present in the request with `Telescope.all(overIfPresent(...), ...)`     |
| `POST /orders/{id}/inspect`                       | Reads the value at a dotted path such as `customer.email` with chained `fieldByName` calls       |
| `POST /orders/{id}/admin-touch`                   | Writes a value at a dotted path with chained `fieldByName` calls and `set`, then saves the order |
| `GET /orders/{id}/redacted`                       | Returns a one-way projection built with `Telescope.from(...).to(...).using(forward, backward)`   |
| `GET /orders/{id}/partner-label`                  | Converts the order to a Lombok `@Data` DTO with a `Mapper<Order, PartnerShippingLabel>`          |
| `PATCH /orders/{id}/from-partner`                 | Overlays the non-null fields of a partial partner label with `partnerLabelMapper.patch(...)`     |

The discount endpoint shows how a mapper joins a navigator path. `OrderTelescope.of().lineItems().each().get()` reaches
every `LineItem`, and `.then(lineItemMapper.asTelescope())` continues the path onto `LineItemEntity`. The controller
then wraps the result in a `LineItemEntityTelescope` and updates `unitPriceCents`, and the mapper converts each new
cents value back to a `BigDecimal` price on the record.

The validated endpoint does not save the order. It returns the order unchanged when every quantity is zero or more.
Otherwise it returns 400 with one error for each negative quantity, through `ValidatedExceptionAdvice`.

The inspect and admin-touch endpoints take the path as a string, so a wrong field name is found only at run time. Both
controllers turn the resulting `IllegalArgumentException` into a 400 response, and the message names the unknown field
and lists the fields that do exist.

### Domain types and how they map

The `orderMapper` bean in `OrderMappers` is built with `Telescope.mapper(Order.class, OrderEntity.class, ...)`. Most
fields match by name and type, so they need no row. The table shows each record field next to its entity field.

| Record field                         | Entity field                                                       | How it maps                                  |
| ------------------------------------ | ------------------------------------------------------------------ | -------------------------------------------- |
| `Order.id: Long`                     | `OrderEntity.id`, generated by the database                        | By name                                      |
| `Order.orderNumber: String`          | `OrderEntity.referenceCode`, stored through `UppercaseConverter`   | `to(Order::orderNumber, ...)` rename         |
| `Order.customer: Customer`           | `OrderEntity.customer`, a lazy `@ManyToOne` `CustomerEntity`       | `via(..., customerMapper)`                   |
| `Order.shippingAddress: Address`     | `OrderEntity.shippingAddress`, an `@Embedded` `AddressEmbeddable`  | By name                                      |
| `Order.billingAddress: Address`      | `OrderEntity.billingAddress`, an `@Embedded` `AddressEmbeddable`   | By name                                      |
| `Order.lineItems: List<LineItem>`    | `OrderEntity.lineItems`, a `@OneToMany` `List<LineItemEntity>`     | `via(..., lineItemMapper)`, applied to each  |
| `Order.giftWrap: Optional<Address>`  | `OrderEntity.giftWrap`, a nullable `@Embedded` `AddressEmbeddable` | By name, empty `Optional` maps to `null`     |
| `Order.metadata: Map<String,String>` | `OrderEntity.metadata`, an `@ElementCollection` map                | By name                                      |
| `Order.payment: Payment`             | None                                                               | `drop(Order::payment)`                       |
| `Customer.tags: Set<String>`         | `CustomerEntity.tags`, an `@ElementCollection` set                 | By name                                      |
| `LineItem.unitPrice: BigDecimal`     | `LineItemEntity.unitPriceCents: long`                              | `to(..., toCents, fromCents)`, 19.99 to 1999 |

Every mapper in the module also passes `writeBeans(SETTERS)`, so each entity is built with its no-argument constructor
and its setters. `Payment` is a sealed interface, and it and each of its subtypes carry `@Bridge` to the matching class
in the `legacy` package. The order mapper leaves `payment` out. `SealedNarrowAfterParadigmHopTest` reads and updates a
card number through it:

```java
Telescope.of(Order.class)
  .field(Order::payment)
  .then(PaymentBridge.BRIDGE)
  .as(CreditCardEntity.class)
  .field(CreditCardEntity::getCardNumber);
```

The partner label mapper converts `Order` to `PartnerShippingLabel`, a Lombok `@Data` class whose `@JsonProperty`
annotations give snake_case JSON names. It renames `orderNumber` to `trackingReference`, converts line items with
`partnerItemMapper`, and leaves out `metadata`, `payment` and, through `drop(Customer::tags, PartnerCustomer.class)`,
the customer's tags. The `telescope-lombok` processor also generates `PartnerShippingLabelTelescope`, which
`PartnerLabelFlowTest` uses to update `customer().email()` on a label.

### Hibernate behaviour

`OrderEntity.customer` is a lazy `@ManyToOne`, so a loaded order holds a Hibernate proxy in that field. Telescope finds
the entity class behind the proxy without loading it, and reading the customer's properties during `backward` loads the
customer once. `OrderCustomerLazyFetchTest` checks this by counting Hibernate entity fetches.

A component whose source and target have the same container type, such as `metadata` and `tags`, is copied into a new
collection rather than shared. Copying a collection, or converting its elements, iterates it, so a lazy Hibernate
collection is loaded at that point and the conversion has to run inside a transaction. The controllers in this module
are `@Transactional`.

## `product-starter`

The `product-starter` module shows `telescope-spring-boot-starter`. The module declares three `@Bean` methods that
return a `Mapper<Product, ?>`, and the starter's auto-configuration indexes every `Mapper` bean in a
`TelescopeMapperRegistry` by its source and target class. The controller does not inject the mappers directly. Instead
it asks the registry for one at request time, e.g. `registry.get(Product.class, ProductDto.class)`.

The three mappers in `ProductMappers` build three different kinds of target:

| Target            | Kind of class                                          | Write hint                                      |
| ----------------- | ------------------------------------------------------ | ----------------------------------------------- |
| `ProductEntity`   | JPA entity with a no-argument constructor              | `writeBeans(SETTERS)`                           |
| `ProductDto`      | Lombok `@Data` class with snake_case JSON names        | `writeBeans(SETTERS)`                           |
| `ProductManifest` | Immutable class with only an all-arguments constructor | `writeBean(ProductManifest.class, CONSTRUCTOR)` |

`writeBeans` sets the default strategy for every bean target in a mapper, and `writeBean` sets it for one class, which
takes precedence over the default.

### Endpoints

| Method and path                                 | What it does                                                               |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| `POST /products?view=dto\|record\|manifest`     | Saves the product, converts it back, and returns it in the requested shape |
| `GET /products/{id}?view=dto\|record\|manifest` | Loads the product and returns it in the requested shape                    |
| `GET /products/{id}/manifest`                   | Loads the product and always returns the `ProductManifest` shape           |

The `view` parameter defaults to `dto`, and any value other than the three listed throws `IllegalArgumentException`. The
`record` view returns the `Product` record itself. For example, posting
`{"sku": "SKU-001", "name": "Widget", "priceCents": 1999}` to `/products` returns the DTO shape, with the id the
database assigned:

```json
{ "product_id": 1, "stock_keeping_unit": "SKU-001", "display_name": "Widget", "price_cents": 1999 }
```

The module uses no annotation processor apart from Lombok, so every conversion goes through the runtime mapper.
`application.yml` sets `telescope.registry.fail-fast: true`, which is also the default. The root README's
[Spring Boot starter](../../README.md#spring-boot-starter) section describes the starter in more detail.

## `org-chart`

The `org-chart` module converts an employee graph that refers to itself. `Employee` is a record with an
`Optional<Employee> manager` and a `List<Employee> reports`. `EmployeeEntity` has a lazy `@ManyToOne` manager and a
`@OneToMany(mappedBy = "manager")` list of reports, so once Hibernate loads both sides, Bob's manager is Alice and
Alice's reports contain Bob. One bean, `Telescope.mapper(Employee.class, EmployeeEntity.class, writeBeans(SETTERS))`,
handles both directions with no rows.

### Endpoints

| Method and path       | What it does                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| `POST /org-chart`     | Converts the record to an entity, saves it with the manager chain, and returns it converted back |
| `GET /org-chart/{id}` | Loads the employee, loads its manager and reports inside the transaction, and converts it back   |

### How cycles are handled

Building the mapper works even though `Employee` contains `Employee`. The mapper records each type pair before it walks
that pair's fields, so when it meets `(Employee, EmployeeEntity)` again it reuses the pair instead of starting over.

Converting a graph that loops back works as well. During one call to `forward` or `backward`, telescope keeps track of
the objects it is still converting on the current path. A reference back to one of those objects maps to `null`, so an
`Optional<Employee>` field becomes `Optional.empty()` and an element of `reports` becomes a `null` element. The list
keeps its size. An object reached along two separate branches is not a cycle, so it is converted twice into two separate
records. A class generated by `@Bridge` cuts a cycle at the same reference, although this module does not use one.

For example, with Alice managing Bob and Bob managing Carol, `GET /org-chart/{id}` for Bob returns the following.
Alice's report back to Bob and Carol's manager back to Bob are both cut:

```json
{
  "id": 2,
  "name": "Bob",
  "manager": { "id": 1, "name": "Alice", "manager": null, "reports": [null] },
  "reports": [{ "id": 3, "name": "Carol", "manager": null, "reports": [] }]
}
```

`JpaCycleMappingTest` builds this graph through Hibernate and checks the first level of Carol's record.
`application.properties` sets `spring.jpa.open-in-view=false`, so every lazy load has to happen inside the controller's
transaction.

### Mapper logging

`MapperLoggingRoutingTest` shows that a mapper's log lines reach Logback through Spring Boot's logging setup. The mapper
logs to `io.github.eschizoid.telescope.mapper.Employee.EmployeeEntity`. At `DEBUG` that logger prints the mapping
structure once, when the mapper is built, and at `TRACE` it also prints the field values of each conversion.

## `invoicing`

The `invoicing` module uses conversion classes that the annotation processor writes at compile time, so no
`Telescope.mapper(...)` call runs and no field names are looked up at run time. `InvoiceLine` and `InvoiceHeader` are
records with `@Focus` and `@Bridge`, and `InvoiceLineEntity` and `InvoiceHeaderEntity` are plain beans with
`@BeanFocus`. The entity classes have no JPA annotations, because the module has no persistence layer.

For each `@Bridge` record, the processor writes a `<Source>Bridge` class with these members:

- Static `forward(source)`, `backward(target)` and `patch(base, partial)` methods.
- `BRIDGE_FN`, a `BridgeFn` that calls the static methods.
- `BRIDGE`, a `Telescope<Source, Target>` that composes with other paths.

By default a bridge requires the source and target properties to match one to one by name, and both pairs here do.
`InvoiceHeader` holds a `List<InvoiceLine>`, so `InvoiceHeaderBridge` builds a new list and converts each element with
`InvoiceLineBridge.forward` or `InvoiceLineBridge.backward`. Because each record also carries `@Focus`, its navigator
gets a method for the bridge, e.g. `InvoiceLineTelescope.of().asInvoiceLineEntity()`, which returns an
`InvoiceLineEntityTelescope` so the path can continue on the entity side.

### Endpoints

| Method and path                   | Generated code it calls                                      |
| --------------------------------- | ------------------------------------------------------------ |
| `POST /invoices/lines/forward`    | `InvoiceLineTelescope.of().asInvoiceLineEntity().read(line)` |
| `POST /invoices/lines/backward`   | `InvoiceLineBridge.backward(entity)`                         |
| `POST /invoices/headers/forward`  | `InvoiceHeaderBridge.forward(header)`                        |
| `POST /invoices/headers/backward` | `InvoiceHeaderBridge.backward(entity)`                       |

After a build, the generated classes are in `build/generated/sources/annotationProcessor/java/main`. For measured
timings of generated bridges against MapStruct and the runtime mapper, see
[Measured performance](../../README.md#measured-performance) in the root README.

## Running the modules

Run any module from the repository root with the Gradle wrapper:

```bash
./gradlew :examples:springboot:order-jpa:bootRun
./gradlew :examples:springboot:product-starter:bootRun
./gradlew :examples:springboot:org-chart:bootRun
./gradlew :examples:springboot:invoicing:bootRun
```

Then send requests to `http://localhost:8080` with `curl` or any HTTP client. To run a module's tests, use
`./gradlew :examples:springboot:<module>:test`. The tests start the Spring application context, and the modules with a
database use an in-memory H2 database.
