# telescope-examples-graphql

A real [graphql-java](https://www.graphql-java.com/) server, served over the JDK's built-in
`com.sun.net.httpserver.HttpServer`, that turns a GraphQL `createUser(input: {...})` argument `Map<String, Object>` into
a typed `User` record. It started life answering one question — **how do you do Map→POJO in a GraalVM native image
without a pile of reflection config?** — and it now also carries telescope's native-image verification: the binary this
module builds is the eight-capability tripwire CI runs on every substrate push (see
[`docs/native-image.md`](../../docs/native-image.md)).

## The three entry points

| Entry point              | What it runs                                             | Run                                                     |
| ------------------------ | -------------------------------------------------------- | ------------------------------------------------------- |
| `RuntimeFromMapServer`   | runtime `Telescope.fromMap(...)` converter               | `./gradlew :examples:graphql:runRuntimeFromMapServer`   |
| `GeneratedFromMapServer` | generated `UserFromMap` (`@FromMap` codegen)             | `./gradlew :examples:graphql:runGeneratedFromMapServer` |
| `NativeVerify`           | eight-capability native-image verifier (the native main) | `./gradlew :examples:graphql:runNativeVerify`           |

The two servers share the `GraphQlServer` harness (schema, JDK `HttpServer`, self-test mutation) and differ only in the
`Map -> User` converter the resolver uses. `GeneratedFromMapServer` uses `UserFromMap` / `AddressFromMap`, generated by
the `@FromMap` processor: a direct `new User(...)` with inline String/int/enum coercion and nested recursion — no
`SerializedLambda`, no `LambdaMetafactory`, no reflection.

## The runtime path under native-image

Runtime `Telescope.fromMap(...)` recovers each field name from its `User::name` method reference via `SerializedLambda`
(reflectively invoking the lambda's `writeReplace`). Under native-image that works only when the class _holding_ the
method references is registered as a lambda-capturing type in a `serialization-config.json` — Wall A in
[`docs/native-image.md`](../../docs/native-image.md). This module registers `NativeVerify` (see
`src/main/resources/META-INF/native-image/...`), so the verifier exercises the runtime path natively.
`RuntimeFromMapServer` is deliberately left unregistered so the unconfigured failure mode stays reproducible:

```
java.lang.IllegalArgumentException: Expected a method reference to a record component / bean property accessor
    at io.github.eschizoid.telescope.internal.LambdaIntrospection.resolveMethodName
    at io.github.eschizoid.telescope.Telescope.fromMap
Caused by: java.lang.NoSuchMethodException: ...$$Lambda/0x...writeReplace()
```

The generated tier has none of that machinery, so it needs no registration at all. That's the practical split: codegen
is native-clean by construction; the runtime path is native-capable with one registration line per call-site class.

## Native build

Requires a GraalVM with `native-image` (Oracle GraalVM, GraalVM CE, Liberica NIK, …). Point `GRAALVM_HOME`/`JAVA_HOME`
at it — the plugin otherwise picks the project's plain-JDK compile toolchain, which has no `native-image`:

```bash
GRAALVM_HOME=/path/to/graalvm JAVA_HOME=/path/to/graalvm \
  ./gradlew :examples:graphql:nativeRun
```

The image entry is `NativeVerify`: it runs all eight capabilities (record field update and read, bean-getter read, the
runtime record→record / record→bean / record→builder-bean mappers, generated `@FromMap`, generated `@Bridge`) and exits
non-zero on any mismatch — so building _and running_ the binary is the test. Config in play: `--no-fallback` plus
build-time init for the model package in `build.gradle.kts`; the telescope packages come from `telescope-core`'s own
`native-image.properties` inside the jar; the module's `reflect-config.json` registers the model types and
`serialization-config.json` registers `NativeVerify`. The whole contract is in
[`docs/native-image.md`](../../docs/native-image.md).

## Layout & tests

```
src/main/java/.../examples/graphql/
  model/    User, Address, Role        — the @FromMap domain records
            Account, AccountEntity     — @Bridge pair (record → bean), also the runtime bean-mapper target
            AccountBuilderBean         — builder-only bean, the runtime builder-mapper target
            UserView                   — same-shape read model, the runtime record-mapper target
  server/   GraphQlServer              — reusable graphql-java + HttpServer harness (serveOnce)
            RuntimeFromMapServer       — runtime-tier server entry point
            GeneratedFromMapServer     — generated-tier server entry point
            NativeVerify               — the native-image verifier (the image main)
src/main/resources/META-INF/native-image/...
  reflect-config.json                  — the model types, for the runtime reflective mappers
  serialization-config.json            — NativeVerify as the lambda-capturing call site (Wall A)
src/test/java/.../examples/graphql/server/
  GraphQlServerTest                    — asserts both server tiers through the harness
```

The entry points just run and print; verification lives in the test and in `NativeVerify`'s assertions:

```bash
./gradlew :examples:graphql:test
./gradlew :examples:graphql:runNativeVerify   # the verifier on the JVM; nativeRun is the real verdict
```
